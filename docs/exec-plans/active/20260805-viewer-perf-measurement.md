## 計測方針

### 基本方針: 本番環境での累積計測

各施策を baseline 単体に個別適用する「独立計測」ではなく、**1 施策 = 1 コミットで積み上げ、デプロイのたびに本番環境で計測する累積計測**を基本とする

| 方式 | 得られる数字 | 採否 |
| --- | --- | --- |
| 独立計測 | 各施策の純粋な寄与 | 補助的に使う。ブランチ管理コストが高く、合計が実測と合わない |
| 累積計測 | 実際に得られた効果の推移 | **採用**。リリース形態と一致し、記事として誠実 |
| 一括計測 | 総合効果のみ | 不採用。どれが効いたか書けない |

累積計測は順序依存を持つ
先に入れた施策が後の施策の効果を食うため、記事では必ず適用順を明示する

計測は**本番環境のみ**で行う
ローカルの `astro preview` や staging は使わない
Cloudflare のエッジ、Brotli 圧縮、HTTP/3 が乗った実際の配信条件でしか出ない数字を記事の主データにする

viewer は Cloud Build → Cloud Run job (`infra/production/docker/viewer/viewer-deploy`) → `wrangler deploy` で配信される
したがって **1 施策 = 1 デプロイ = 1 計測**のサイクルになる

### 計測条件 (固定する)

- **n = 9 の中央値**を採る。本番計測は回線とエッジの分散が大きいため、n=5 では中央値が安定しない。併せて IQR も記録し、差が誤差でないことを示せるようにする
- スロットリングを固定する。設定値は `tools/perf/measure.ts` の `PRESETS` に直接書き、Lighthouse の既定値の変更に引きずられないようにする
- **mobile と desktop の両方**で計測する。ボトムナビを持つモバイル主体のサイトだが、CPU スロットリングの有無で JS 系施策の見え方が変わるため両方残す
- 計測時刻を記録する。時間帯による差を後から切り分けられるようにする
- commit hash は記録しない。計測対象は本番にデプロイされた成果物であり、手元の HEAD とは対応しないため。施策の識別は `--label` で行う
- 計測対象ページを固定する (`tools/perf/pages.json`)
  - `/` — トップ
  - `/songs/` — 楽曲一覧。全件をカードで描画する最も重い一覧
  - `/releases/` — リリース一覧
  - `/songs/[songId]/` — 楽曲詳細の**最も重い 1 件**
  - `/releases/[releaseGroupId]/` — リリース詳細の**最も重い 1 件**。トラックリストを持つ
  - `/media/[mediaId]/` — メディア詳細の**最も重い 1 件**。LCP 要素がサムネイル
  - `/contact/` — 対照ページ。固有コンテンツがほぼ無く、共通オーバーヘッドの削減がそのまま出る
  - `/site-policy/` — 対照ページ。テキストのみで画像も hydration も無い

静的ページは上の 5 枚で全数である
`_profile.astro` と `media/_index.astro` は `_` 始まりで Astro のビルド対象外なので、media 一覧ページは存在しない

#### 詳細ページの代表の選び方

**songs / releases / media から必ず 1 枚ずつ選ぶ**
ページ種別ごとに支配的な要因が違うため、1 種別でも欠けるとその要因の効果が計測から漏れる

選定基準は `perf:scan` の実測 LCP が**最も遅いもの**とする
最悪ケースが改善したかを見たいので、中央値付近ではなく最遅を採る

- ID が壊れているページ (UUID に `efbfbd` = U+FFFD が混入) は選ばない
- 一度選んだら計測期間中は固定する

当初は「HTML サイズの中央値」で選んでいたが、スキャンの結果このリリース詳細は 85 件中 77 位 (ほぼ最速の部類) だった
転送量からページの遅さは予測できないため、実測で選び直す

対照ページ 2 枚を入れているのは、G1 (全ページ共通の固定オーバーヘッド) の効果を他の要因から切り離して示すため
この 2 枚は固有コンテンツがほとんど無いので、削減分がそのまま数字になる

### 本番計測の前提条件

#### コンテンツドリフト対策 (最重要)

viewer は SSG で、**ビルド時に本番 API を叩いて生成**する
計測期間中に楽曲やリリースが増えると HTML が太り、施策の効果と混ざる
「CSS を削ったのに HTML 転送量が増えた」の原因が実は楽曲追加だった、という事故が最も起きやすい

- 各計測時点の**件数 (楽曲数 / リリース数 / メディア数) を必ず記録する**
- 計測期間中はデータ追加を止める。止められない場合は追加のタイミングを記録し、記事で断りを入れる

#### キャッシュ状態を揃える

デプロイ直後の初回リクエストはコールドで TTFB が跳ねる

- デプロイ完了から計測開始までの待ち時間を固定する
- 本計測の前に対象 4 URL を数回叩いてウォームアップする
- レスポンスヘッダ (`cf-cache-status` / `age` / `content-encoding`) を記録し、状態が揃っていない回は捨てる

#### 圧縮後と圧縮前の両方を記録する

本番は Brotli 圧縮が効くため、issue に書かれた生サイズの削減率 (例: #921 の HTML -90%) がそのまま出るとは限らない
SVG のような圧縮の効きやすいリソースは、圧縮後の差が生サイズの差よりかなり小さくなる

Lighthouse の `transferSize` (圧縮後) と `resourceSize` (圧縮前) を**両方**記録し、記事では両方を提示する

### 記録する指標

ラボ指標だけでなく転送量も残す
LCP が動かなくても転送量が減っていれば記事の材料になる

- LCP / FCP / CLS / TBT / Speed Index / TTFB / Performance スコア — それぞれ中央値と IQR
  - INP はフィールド指標でラボ計測では出ないため、TBT を代理指標にする
- resourceType 別の転送量 — 圧縮後 (`transfer`) と圧縮前 (`resource`) の両方
- リクエスト数、クリティカルチェーンの深さ
- 楽曲数 / リリース数 / メディア数 (ドリフト検出用)
- キャッシュ状態 (`cf-cache-status` / `age` / `content-encoding`)

### 記録フォーマット

`docs/perf/results.jsonl` に 1 計測 1 行で追記する

```json
{"label":"baseline","formFactor":"mobile","page":"contact","url":"https://isekaijoucho.fan/contact/","measuredAt":"2026-08-05T15:50:19.608Z","runs":9,"headers":{"cacheStatus":"HIT","encoding":"zstd"},"counts":{"songs":380,"releases":85,"media":831},"metrics":{"lcp":{"median":0,"iqr":0}},"transfer":{"Document":0,"Font":0},"resource":{"Document":0,"Font":0},"requests":0,"criticalChainDepth":4}
```

記事のグラフはこのファイルをそのまま入力にできる

### 計測ツール

探索と計測でツールを分ける

| | `unlighthouse` (探索) | `lighthouse` 直接呼び出し (計測) |
| --- | --- | --- |
| 目的 | 全ページから遅いページを見つける | 施策の前後比較 |
| 対象 | サイト全ページ (約 1300) | `pages.json` の固定 8 ページ |
| 実行 | 並列 4、1 ページ 1 回 | 直列、1 ページ 9 回 |
| 出力 | 順位 | 中央値と IQR |
| 頻度 | baseline と最終形の 2 回 | 施策ごと |

#### 探索: `tools/perf/unlighthouse.config.ts` + `rank.ts`

固定 8 ページだけでは、詳細ページ 1298 枚の中にある遅いページを取りこぼす
baseline でも転送量がほぼ同じ song-detail (3049ms) と release-detail (5376ms) に 2.3s の差があり、転送量からは遅さを予測できていない

- 動的ルートの間引き (`dynamicSampling`) を無効化し、全件を走査する
- `rank.ts` がルート種別ごとに LCP の遅い順で並べ、`pages.json` に載せるページを選ぶ材料にする

**この数値は記事のグラフには使わない**
並列クロールで下振れし、`/releases/` で 8.2s (計測) に対し 17.2s (探索) という差が出ている
unlighthouse は自前の Chrome を使うため puppeteer 同梱版ともバージョンが異なる
順位付け以外の用途には使わない

#### 計測: `tools/perf/measure.ts`

`lighthouse` を直接叩くスクリプトを置く

- TypeScript で書き、Node 24 の型ストリップでそのまま実行する (`node measure.ts`)
- n=9 を**直列**実行し、中央値と IQR を算出する
- 全 run の生レポート JSON と中央値 run の HTML レポートを `docs/perf/reports/` に残す
  - JSON は [Lighthouse Viewer](https://googlechrome.github.io/lighthouse/viewer/) で後から開き直せる
  - `reports/` は 1 計測あたり数百 MB になるため git 管理から外す
- クリティカルチェーンの深さは `network-dependency-tree-insight` から算出する
  - Lighthouse 13 で `critical-request-chains` は廃止された

WSL に Linux Chrome がないため、puppeteer 同梱の Chromium を使いバージョンごと固定する

数字が想定外に動いたときの原因究明には `web-perf` スキル (Chrome DevTools MCP) を使う
バッチ計測には使わない

## 適用順と食い合いの注意

期待効果が大きい順に積む
そのため後発の施策ほど数字が小さく出る点を記事側で注記する

baseline の予備計測で、**フォントが圧倒的に支配的**であることが分かった (下記)
issue の記述から想定していた「#921 が単体最大」は生サイズの話で、圧縮後の実測ではフォントが桁違いに大きい
これを受けて #923 を先頭に置く

1. #923 (G2) — フォントチェーンの解消。**実測上の最大要因**
2. #921 (G1) — HTML の固定オーバーヘッド削減。対照ページ 2 枚に素直に出るはず
3. #927 (G1) — `is:inline` の削減。#921 と同じ軸なので相対効果は小さく出る想定
4. #934 (G2) — CSS 削減。#923 の後なので相対効果は小さく出る想定
5. #925 (G3) — LCP 要素。G1/G2 で既にペイントが早まっている分だけ縮む
6. #924 (G4) — TBT。指標が独立なので素直に出るはず
7. G5 の施策 (#922, #926, #928, #929, #930, #931, #932, #933) — 計測対象外なのでまとめて適用する

3 と 4 と 5 は効果が消えた場合に **baseline 単体での追加計測**を行う
「単体では -200ms 出るが #921 と #923 の後では -20ms しかない」という比較は記事の中心的な材料になる

G5-b (#929 / #931 / #930) は悪化方向なので、適用前後で 1 度だけ計測して「a11y と SEO のために払ったコスト」を数字で押さえる

### 改善余地の構図

| 要因 | 影響範囲 | 規模 (圧縮後) |
| --- | --- | --- |
| 画像 | releases 系と top / song-detail | 最大 15.5MB/枚 |
| フォント (CSS 239KB + woff2) | **全ページ** | 856KB〜2.5MB |
| HTML | 全ページ | 13〜40KB |

画像は 1 ページあたりの規模が最大、フォントは全ページに必ず乗る固定費
どちらも既存 issue が想定していた HTML 削減より 2 桁大きい

### 想定と実測の食い違い

- **Stylesheet 239KB の内訳は Google Fonts の CSS が 238KB (圧縮前 935KB)**、viewer 自身の CSS は 10KB (圧縮前 43KB) しかない
  - Noto Serif JP を 5 ウェイト要求しているため、グリフサブセットごとの `@font-face` が大量に生成される
  - `unused-css-rules` が指す 238KB もこれ。つまり #934 (viewer.css 棚卸し) の対象は全体の 4% でしかない
- **フォント関連 (CSS 238KB + woff2 617KB〜2241KB) が全ページで支配的**。`/contact/` では総転送量 900KB のうち 855KB (95%) を占める
  - グリフ単位のサブセット配信のため、日本語タイトルが多いページほど際限なく増える (songs-index で woff2 が 72 リクエスト)
- **HTML は zstd で約 14 倍に圧縮される**。issue の「HTML -90%」は生サイズの話で、圧縮後は 186KB → 13KB と既に小さい。#921 / #927 の効果は生サイズほど劇的には出ない
- **TBT が全ページ 0ms、Script 転送量も 24〜26KB** しかない。#924 (hydration / prefetch) にラボ上の伸びしろがほぼ無い
- 単純なページでは **LCP = FCP** が一致し、mobile では全ページ約 3035ms で揃う。つまり LCP はレンダーブロッキングの固定コストそのもの
- クリティカルチェーンの深さは全ページ **4** で、issue の指摘 (HTML → CSS → fonts CSS → woff2) と一致する

### issue に無い最大の問題: リリースジャケット画像

画像転送量は一覧で mobile 5.1MB / desktop 9.3MB、詳細 1 枚で **15.5MB** に達し、他のどの要因より大きい

- desktop releases-index の LCP IQR 4805ms (829ms〜8699ms) もこれが原因

#921〜#936 のどの issue もこれを扱っていないため #957 を新規に起票した

計測条件を揃えるために baseline ごと取り直した最終版

### 結果

| ページ | mobile LCP (IQR) | desktop LCP (IQR) | 総転送量 (mobile) |
| --- | --- | --- | --- |
| top | 5272→6315 (503→615) | 997→1048 (63→125) | 1450→1191KB (-18%) |
| songs-index | 9953→13247 (9906→9594) | 4885→5265 (2193→309) | 2781→2912KB (+5%) |
| song-detail | 11208→**3471** (3188→1051) | 999→1065 (45→98) | 2333→1179KB (-49%) |
| releases-index | 11951→**7519** (7188→1048) | 4288→**3152** (3158→1021) | 6801→2084KB (-69%) |
| release-detail | 85845→**4569** (1155→1198) | 15090→**1400** (231→389) | 16386→937KB (-94%) |

Performance スコアは desktop release-detail が 0.73→**0.94**、mobile song-detail が 0.69→0.83

### 分かったこと

- **画像を持つ 3 ページで大きく改善した**。release-detail は 3000x3000 の PNG 1 枚 15.5MB が 25KB になった
- **転送量が減ると分散も収まる**。releases-index の IQR は mobile 7188→1048、desktop 3158→1021
  - 重い画像はページの遅さだけでなく、計測のばらつきの原因でもあった
- **対照ページ 2 枚は ±2% 以内**。計測が正しく機能している証跡になる
- **mobile の top は +20%**。3 回の計測で +10% / +18% / +20% と一貫しており、ノイズではない
  - LCP 要素は変換した画像ではなく YouTube のサムネイル
  - `sizes` を実枠に合わせた結果 480w (15KB) から 640w (60KB) になった
  - 表示枠 372px x DPR1.75 = 651 device px に対し baseline は 480w を配信していた。退行ではなく解像度不足の是正
- **mobile の songs-index は判定不能**。IQR 9594 で中央値の差より大きい
  - このページの画像は YouTube サムネイルでジャケット変換の対象外。転送量も +5% しか動かない

### `sizes` は CSS の実寸から計算する

`sizes` を丸めて書くと srcset が 1 段上の variant を選ぶ
291px の枠に `330px` と宣言した結果、YouTube サムネイルが 320w から 480w になり desktop の転送量が 366KB から 737KB に増えた

グリッドの列数・gap・shell の padding から `calc()` で組み立てると解消する

| 用途 | sizes |
| --- | --- |
| 楽曲タイル | `calc((min(1480px, 100vw) - 180px) / 4)` (4 カラム, gap 28px, padding 48px) |
| リリースカード | `calc((min(1480px, 100vw) - 160px) / 3)` (3 カラム, gap 32px, padding 32px) |
| 1 カラム時 | `calc(100vw - 40px)` (800px 以下は padding 20px) |

### variant は少なくする

変換は variant ごとに初回リクエストで生成され、そのとき約 0.45 秒の固定コストがかかる

| 原本 | コールド変換 | ウォーム |
| --- | --- | --- |
| 3000x3000 PNG 15.1MB | 0.60〜0.79s | 0.19s |
| 1400x1400 JPEG 190KB | 0.48〜0.60s | - |
| 720x720 WebP 67KB | 0.46〜0.48s | - |

原本サイズが 225 倍違っても 0.23 秒しか変わらない
削減できるのは原本を小さくすることではなく、variant の種類を絞って暖まっている確率を上げること

実測した表示枠から必要な device px は最大 651 なので、320 と 640 の 2 段で足りる
当初の 320 / 640 / 1280 では mobile のトップと一覧が 1280 を取得していた

確実に効くのはデプロイ時のプリウォームで、これは今後の課題として残す

### AVIF と WebP

`format=auto` は AVIF を返す
quality=80 での出力サイズはほぼ同じで、WebP を選ぶ理由があるとすればデコードの速さであってサイズではない

| 画像 | width | AVIF | WebP |
| --- | --- | --- | --- |
| 3000x3000 PNG | 640 | 69907 | 78674 |
| 2205x2207 JPEG | 640 | 134796 | 135342 |

- **mobile の約 3.2 秒の FCP はフォント由来だった**。全 16 ケースで 31〜47% 改善し、事前の想定が裏付けられた
  - 対照ページは LCP = FCP なので効果が直接読める (contact は -45%)
- **圧縮後の転送量では CSS はあまり減らない**と見ていたが、実際は 249KB → 98KB (-61%) 減った
  - `@fontsource` は使うバリアントだけを取り込むため、Google Fonts が全バリアントの `@font-face` を返すのとは量が違う
- **LCP 要素が画像のページでは LCP が悪化した**
  - テキストが LCP のページ (contact / site-policy) は -39〜-45%
  - 画像が LCP のページ (top / releases-index / media-detail) は +19〜+36%

  - フォントのリクエスト数が増えている (30→37)。`@fontsource` は Google Fonts より細かい unicode-range で分割配信する
  - ただし contact (26→26) と releases-index (52→52) はリクエスト数が同じで結果が逆なので、リクエスト数だけでも説明できない

  - LCP 画像は現在も `loading="lazy"` のままなので、#925 (eager + fetchpriority) が直接この問題を狙う
  - そのため適用順を変更し、#921 より先に #925 を当てて答え合わせをする

## 施策 3: 画像変換のゾーン選択と preconnect

`#951` が別実装の画像変換 (`shared/image.ts`) を持っていたため、どちらが速いかを実測して決めた

### 変換ゾーンの比較

| ゾーン | 形式 | コールド変換 | ウォーム |
| --- | --- | --- | --- |
| viewer | `/cdn-cgi/image/.../<絶対 URL>` | 0.60〜0.77s | 0.135s |
| assets | `<origin>/cdn-cgi/image/...<path>` | **0.15〜0.16s** | 0.140s |

viewer ゾーンは変換元を別ゾーンから取りに行くため初回生成が 4 倍遅い
一方 viewer ゾーンなら画像が HTML と同一オリジンになり、既存の接続を再利用できる

### 実測 (`923-self-host-fonts` → `957b-assets-zone`)

assets ゾーンへ移すとオリジンが 2 つから 3 つに増える
**接続確立は固定コストなので、画像枚数で符号が変わった**

| 画像枚数 | ページ | mobile | desktop |
| --- | --- | --- | --- |
| 4 枚 | releases-index | -7% | **-22%** |
| 2 枚 | song-detail | +183% (IQR 3335, 判定不能) | -10% |
| 1 枚 | release-detail | **+131%** | **+114%** |
| 0 枚 | contact / site-policy 他 | ±5% 以内 | ±9% 以内 |

枚数が多いページでは接続コストが償却されて別オリジンの並列性が勝ち、1 枚のページでは丸ごと LCP に乗る

### preconnect (`957c-preconnect`)

`<link rel="preconnect">` で接続確立を前倒しした

| ページ | 923 (viewer) | 957b (assets) | 957c (preconnect) |
| --- | --- | --- | --- |
| release-detail (mobile) | 2788 | 6446 | 5235 (-19%) |
| release-detail (desktop) | 889 | 1905 | 1695 (-11%) |
| song-detail (mobile) | 2391 | 6776 | 3758 (-45%) |
| releases-index (mobile) | 10243 | 9525 | 9581 |
| releases-index (desktop) | 3176 | 2487 | 2875 |
| top (mobile) | 7542 | 7923 | 6098 (-23%) |

**画像 1 枚のページは preconnect でも viewer ゾーンの水準まで戻らない** (923 比で +88〜+91%)
別オリジンの接続コストを完全には隠せないという構造的な限界がある

### 決定

**assets ゾーン + preconnect を採る**

- 一覧ページを重視する方針に合う (releases-index は 923 比で mobile -6% / desktop -9%)
- 詳細ページの不利は preconnect で 2〜4 割戻せる
- release-detail は 923 比では +88% だが、baseline (85845ms) 比では依然 -94%
- コールド変換の 0.5 秒問題が消えるため、デプロイ時プリウォームが不要になる
