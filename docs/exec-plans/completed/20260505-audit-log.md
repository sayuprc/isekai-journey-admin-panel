# 管理画面操作の監査ログ基盤導入

## Status

completed

## Background

管理画面で誰がいつ何を作成・更新・削除したか、またログイン・トークンリフレッシュを行ったかが追跡できない。
現状は物理削除のため、削除されたデータの存在自体が痕跡として残らない。
不正操作・誤操作の調査や、運用上の事実確認のために、書き込み系操作の履歴を残す必要がある。

## Goal

管理画面の書き込み系 UseCase（作成 / 更新 / 削除 / ログイン / トークンリフレッシュ）から呼び出すと、
「誰が・何を・どうした」を変更後スナップショット付きで記録できる監査ログ基盤を導入し、
既存の対象 UseCase からその基盤を呼び出すように改修する。

## Scope

- `Support` パッケージ配下に監査ログ機構を追加（横断的関心事のため、既存の `Clock` / `DbTransaction` / `Authorizer` と同じ層に置く。独立パッケージにすると AuditLog → 各パッケージへの逆流依存が発生するため避ける）
  - Domain: `Support/Domain/AuditLog/` に `AuditLog` エンティティ、操作種別 (`Create|Update|Delete|Login|Refresh`)、対象種別の値オブジェクト
  - Contracts: `Support/Contracts/AuditLog/AuditLogRecorderInterface.php`（各 UseCase から呼ぶ I/F）
  - Infrastructures: `Support/Infrastructures/AuditLog/` に Eloquent 実装、DI バインディング
- 新規テーブル `audit_logs` をマイグレーションで追加
  - カラム: `id`, `admin_user_id`（実行者）, `action`（create/update/delete/refresh）, `target_type`, `target_id`, `snapshot`（JSON、変更後スナップショット）, `created_at`
  - Refresh の場合は `target_type=AdminUser` / `target_id=自分の admin_user_id` を記録（null にしない）
  - 監査ログ記録失敗時は本処理ごとロールバックする方針（同一トランザクション内で書き込む）
- 既存の書き込み系 UseCase へ監査ログ呼び出しを組み込む
  - `Person`: `Create/Update/Delete`
  - `Song`: `Create/Update/Delete`
  - `Song/Tag`: `Create/Update/Delete`
  - `Auth`: `Refresh`（成功時）
- 認証ユーザーの取得は `Auth\Infrastructures\Auth\AuthorizedAdminUser` 経由を想定
- バックエンド規約 `.claude/rules/01-backend.md` に従い、業務エラーは ResultType、テストは DatabaseTestCase 等で記載

## Non-Scope

- 論理削除化（行わない。物理削除のままで、削除事実は監査ログにのみ残す）
- before/after diff の保存（変更後スナップショットのみ）
- 閲覧 UI（管理画面で監査ログを参照する画面）
- 閲覧用 API エンドポイント
- ログイン (`Authenticate`) の記録（記録量が多くなりすぎ、運用上の価値が低いため今回は対象外）
- ログイン失敗の記録
- `AdminUser` の Create UseCase（実装が今後変更予定のため、組み込みは新実装と同時に行う）
- `logout` UseCase（現状未実装のため対象外）
- Eloquent model events / ドメインイベントによる自動記録（各 UseCase からの明示呼び出しに統一）
- 既存パッケージの読み取り系 UseCase（Get / List / Search）への組み込み

## Acceptance Criteria

- `audit_logs` テーブルがマイグレーションで作成され、`admin_user_id`, `action`, `target_type`, `target_id`, `snapshot`, `created_at` を持つ
- `Support/Contracts/AuditLog/AuditLogRecorderInterface` と `Support/Infrastructures/AuditLog/` の実装が存在し、DI コンテナに登録されている
- Person の Create/Update/Delete UseCase 実行時に、対応する監査ログ 1 件が `action`・`target_type=Person`・`target_id`・変更後スナップショット JSON とともに記録される（Delete 時は削除前の最終状態をスナップショットとする）
- Song および Song Tag の Create/Update/Delete UseCase 実行時に、同様に 1 件記録される
- `Refresh` UseCase が成功した場合、`action=refresh`・`admin_user_id`・`target_type=AdminUser`・`target_id=自分の admin_user_id` で 1 件記録される
- 監査ログの書き込みが失敗した場合、本処理（対象 UseCase 全体）がトランザクションごとロールバックされ、業務データも記録もどちらも残らない
- 各 UseCase に対するインテグレーションテストで、上記の記録が `audit_logs` に存在することが検証されている

## Decision Log

- 2026-05-05: 監査ログ機構を独立パッケージにせず `Support` 配下に置く。理由: 監査ログは横断的関心事であり、AdminUser/Person/Song/Auth から共通に依存される。独立パッケージ化すると AuditLog → 各業務パッケージへの逆流依存（ターゲット種別や実行者参照のため）が発生する。`Clock` / `DbTransaction` / `Authorizer` と同列の位置づけとする。
- 2026-05-05: 監査ログの記録を対象 UseCase の業務処理と同一トランザクション内で行う。理由: 業務データは保存されたが監査ログは欠損する／逆のケースが発生すると、調査・運用上の信頼性が崩壊する。Recorder 内部でトランザクションを張らず、呼び出し側の `TransactionInterface::scope` に乗ることで実現する。
- 2026-05-05: スナップショットからは機密情報を除外する。具体的には `AdminUser` の `password` / `plainPassword`、リフレッシュトークンの平文 / ハッシュ値を含めない。理由: 監査ログは閲覧権限が広く、機密情報を保持するとログ自体が攻撃面になる。
- 2026-05-05: Eloquent イベント / ドメインイベントによる自動記録は採用せず、各 UseCase からの明示呼び出しに統一する。理由: 「いつ・何を記録したか」が UseCase コードを読めば分かる方が監査要件に対する説明責任を果たしやすい。また、暗黙の副作用に依存しないことで `Domain` 層を純粋に保てる。
- 2026-05-05: Recorder I/F は実行者 ID を引数で受け取る。理由: AuthContext は HTTP ミドルウェアが認証済みユーザーを伝搬するための仕組みであり、Recorder（Support 層の汎用機構）が AuthContext に依存するのは責務違反。Authenticate / Refresh のように AuthContext 未設定の場面でも UseCase が能動的に AuthContext::set を呼ぶ必要がなくなる。呼び出し側で実行者を渡す重複は許容する。
- 2026-05-05: テーブル定義は Atlas スキーマで管理する（既存規約に従う）。Laravel migrations は使用しない。
- 2026-05-05: 計画上 `AuditLogRecorderInterface::record()` の第1引数は `AdminUserId` だったが、`Support\Contracts` コンポーネントは Arkitect ルール上 `AdminUser\Domain` への依存が許可されていない（`SupportComponent::Contracts` は依存先なし）。`record()` の actor 引数は `string $actorId` に変更し、`target_id` と表現を揃える。
- 2026-05-05: `AuditAction` / `AuditTargetType` enum は `Support\Domain\AuditLog\` ではなく `Support\Contracts\AuditLog\` に置く。理由: `AuditLogRecorderInterface` のシグネチャ型として参照する必要があるが、`SupportComponent::Contracts` は他コンポーネントへの依存を一切持たないため、enum を `Support\Domain` に置くと Recorder I/F から参照できない。
- 2026-05-05: `AuditLog` / `AuditLogId` / `AuditSnapshot` の Domain エンティティ・値オブジェクトは新設しない。Recorder が actor/action/target/snapshot のプリミティブを受け取り Eloquent モデルへ INSERT する設計のため、Domain エンティティを介在させる利益がなく、Domain → Contracts の逆流依存も避けられる。Eloquent モデル `App\Models\AuditLog` で永続化責務を完結させる。
- 2026-05-05: `AuthServiceProvider` の追加 `bind` は不要だった。`AuthenticateUseCase` / `RefreshUseCase` は明示的 bind がなく Laravel コンテナの自動解決に任せているため、コンストラクタ引数の追加だけで動作する。
- 2026-05-05: 計画では Person Delete を transaction なしのままにしていたが、監査ログ書き込みを業務処理と同一トランザクションに乗せる方針上、Person Delete UseCase に `TransactionInterface` を導入して `transaction->scope` 内で削除＋ログ記録を行うように変更した。Song Delete / SongTag Delete も同様。
- 2026-05-05: 監査ログの actor 取得は `AuthContext::get()->adminUserId` を使う。`UseCaseAuthorizer` は `AuthorizableUserInterface` のみを返し管理ユーザーIDを露出しないため、各 UseCase に `AuthContext` も DI する。AdminUser Create UseCase は元々 `Authorizer` を持たないため、`AuthContext` のみ追加。
- 2026-05-05: レビュー指摘により、`AuthenticateUseCase` の login スナップショットから `refreshTokenId` を除外し `['email' => ...]` のみとした。計画 Step 9 の記載に合わせるため。
- 2026-05-05: レビュー指摘により、`AuthenticateUseCase` の `$this->context->set($foundUser)` を `transaction->scope` の外側へ移動した。元々 AuthContext::set はこの UseCase の既存処理だが、scope 内で context を読み取らない（recordLogin は引数で `$foundUser` を受け取る）ため scope 内に置く必要がない。Refresh で確認した「AuthContext は HTTP ミドルウェアの責務」方針とは別に、既存処理として残す判断で scope 外へ出した。
- 2026-05-05: レビュー指摘（Minor）の `audit_logs` の index 名 `fk_audit_logs_admin_user_id` は、リポジトリ既存スキーマ（`refresh_tokens` / `song_persons` / `song_taggings` 等）の慣行と一致しているため変更しない。これらは index と foreign_key を同名で定義する命名規則を採用している。
- 2026-05-05: レビュー指摘により、`AuditLogRecorder` を `Model::query()->insert()` から `AuditLog::create([...])` に変更し、`snapshot` の cast (`'snapshot' => 'array'`) を経由してエンコードされるようにした。`AuditLog` モデルに `$guarded = []` を追加（mass assignment のため）。`$timestamps = false` のため `created_at` は引数の値がそのまま入る。
- 2026-05-05: ユーザー判断により、`AdminUser` Create と `Authenticate` (login) の監査ログ呼び出しを撤去。理由: AdminUser Create は実装変更が控えており、新実装と同時に組み込む方が合理的。Authenticate (login) は記録量が多くなる割に運用上の価値が低いため対象から外す。`AuditAction::Login` enum も削除。Refresh の記録は維持。
- 2026-05-05: Unit テストのコンストラクタ Mock を追従修正した（Song/SongTag/Person の Create/Update/Delete に `TransactionInterface` / `AuditLogRecorderInterface` / `AuthContext` の DI を追加し、SongTag Delete は対象不在時に `Ok(null)` を返す既存の冪等仕様を復元）。
- 2026-05-05: Recorder I/F の actor 引数を末尾オプショナル `?string $actorId = null` に変更し、未指定時は `AuthContext` から解決する設計に変更。HTTP 経由の UseCase（Person/Song/SongTag）から `AuthContext` 依存を削除した。`Login`/`Refresh` は AuthContext 未設定の文脈なので引数で actor を明示渡しする。`UseCaseAuthorizer` も既に `AuthContext` を読んでおり、Recorder が読むのは前例に倣った形。
- 2026-05-05: Song 系 UseCase の audit log スナップショットを `AssembledSong` から `Song::toArray()`（集約のシリアライズ）に変更。Person / SongTag は元から集約の `toArray()` を使っており、Song だけ Assembler 経由で食い違っていた。Assembler は API 提示用 DTO で typeName 等の denormalize 値を含むが、監査ログには集約の素の状態（ID と素の値）が適切。Delete UseCase からは Assembler 依存自体を削除（OutputData が不要なため）、Create/Update は OutputData 用に Assembler 依存を残す。スナップショットのキーが camelCase から snake_case（`song_id` 等）に変わった点は集約の `toArray()` 実装に従う。
- 2026-05-05: 監査ログスナップショットの方針: **Entity を記録するときは原則として集約の `toArray()` をそのまま使う。機密情報（パスワード、平文/ハッシュトークン等）を含む集約のときだけ手組みでフィルタする**。理由: 集約は永続化単位の Source of Truth であり、`toArray()` を使えば集約の構造変更が監査ログに自動追従する。手組みは集約とログの両方をメンテする二重管理になる。Login/Refresh は `RefreshToken` 集約に平文/ハッシュトークンが含まれるため例外的に手組み（`refreshTokenId` のみ）。
- 2026-05-05: `AuditLogRecorderInterface` と関連 enum (`AuditAction` / `AuditTargetType`) を `Support\Contracts\AuditLog` から `Support\UseCase\AuditLog` 配下へ移動。`SupportComponent::UseCase` は `AdminUser\Domain` と `Support\Domain` に依存できるため、`actorId` を `AdminUserId`、`targetId` を `UuidValueObject`（PersonId/SongId/SongTagId/AdminUserId の共通基底）で型強化できるようになる。Contracts は依存先ゼロというルールを保ちつつ、I/F の表現力を上げる狙い。`SupportComponent::UseCase` の deps に `Support\Contracts` と `Support\Domain` を追加。
